# ScenarioWriter — Idel-DreamMaker 分支人生副本生成

## 这是什么

为挂机游戏 Idel-DreamMaker 创作副本（剧本）。每个副本 = 一次完整的人生经历，500 个等级，每升一级弹出故事。关键节点做选择，影响后续剧情走向。

**三种模式（进入时先问用户选哪种）：**

| 模式 | 触发 | 说明 |
|------|------|------|
| **原创模式** | 用户没有素材，从零构思 | 先聊设定 → 规划 → 小批生成 |
| **改编模式** | 用户提供小说/剧本/大纲 | 走改编指南（references/adaptation-guide.md） |
| **续写模式** | 上次生成中断/要跨会话继续 | 读状态文件从断点续写，见"跨会话"章节 |

## 数据规格

| 项目 | 值 |
|------|-----|
| 普通 story | ~500/分支（周目 = 一条分支路径） |
| choice 事件 | 10-15/分支（关键节点让你选） |
| choice target | 20-45/分支（选完后的分支剧情） |
| 事件类型 | story（剧情，升级时触发） |
| 文本长度 | 30-80 字 |
| 叙事人称 | 第二人称"你" |
| 称号 | 30 个/副本 |
| 成就 | 50 个/副本 |
| 节日事件 | 约 52 条/副本 |
| 多周目重生 | 默认单周目（max_rebirth 默认 0），最多 3（4 周目）。**注意：引擎暂不按 MinRebirth 区分周目内容**（重生后重玩相同剧情），新副本建议单周目起步 |
| 挂机机制 | standard / cultivation / cyber / tide / polar 五种 |
| 数值 flag | `attitude_*` 0-100（态度值，可选） |

> 注意：filler（日常填充事件）机制已废弃（v3.4.0 移除），**不要生成 filler 类型事件**。

## 游戏机制简介

- 等级曲线：Lv.1-100 平方根公式，Lv.100+ 等差数列（公式统一在 `level-curve.cjs`）
- Lv.500 触发结局弹窗；结局按"分支 + flag 条件"选择（见结局规划表）
- 分支：Lv.5 强制 4 选 1 进入分支（choice target 带 Branch 列切换）
- 重生经验加成：每次 +25%，封顶 +100%
- flag 系统：FlagSet 设置 / FlagRequire 判断；`;` 与 `&` 都是 AND，`|` 是 OR；裸 flag 名=存在即 true；值统一字符串比较（`'false'` 字面量可用）

## 规划阶段（所有模式共用，顺序执行）

### Stage 1：确定副本设定

1. 问用户想写什么主题
2. 理解世界观设定，推荐挂机机制
3. 确定元数据（id / name / name_cn / description / player_title / mechanic / max_rebirth / completion_title）
4. 输出预览等用户确认

### Stage 1.5：节奏分段（自定义，不硬套模板）

**规则：等级是容量，节奏由内容决定。** 按故事结构定义分段，只守三条硬约束：
1. 故事从 Lv.1 开始铺垫，不能跳过开头
2. Lv.500 是结局——最后一段（约 30-50 级）留给"高潮→收尾→结局"递进
3. choice 均匀分布（不能全堆在某一段）

**模板参考（可自由改）：**

| 模板 | 分段 | 适合 |
|------|------|------|
| 五段式 | 开端1-50/成长51-150/鼎盛151-300/沉淀301-450/终章451-500 | 人生传记类 |
| 三幕式 | 建立1-150/对抗151-350/收尾351-500（比例可调） | 冒险/战争类 |
| 慢热式 | 长铺垫1-200/展开201-430/收尾431-500 | 悬疑/日常类 |

输出分段表（等级区间 → 阶段名 → 叙事任务），等用户确认。

### Stage 1.6：choice 三层设计 + 规划表（最大确认点）

**choice 三层设计（每个 choice 先定层，再写）：**

| 层 | 游戏机制 | 写法 |
|----|---------|------|
| 态度选择 | 数值 flag（0-100） | FlagSet 用 `attitude_xxx+=10` / `-=10`；后续事件 FlagRequire 用 `attitude_xxx>=60` 判断文本变体；不影响分支和结局 |
| 路径选择 | branch 切换 / a-b 平行线 | choice target 事件带 Branch 列（切分支）；或 target 走 15 级平行线后汇合 |
| 命运选择 | 关键 flag | FlagSet 设 `saved_xxx=true` 类 flag；决定 Lv500 结局归属 |

**必须输出的四张表（全部给用户确认，确认后写进状态文件不再变动）：**

1. **世界观锚点表**（治"剧情单薄"，全设数量下限）：
   - 角色：主角 1 + 核心配角 3-5（各有弧线：出场→变化→结局）+ 次要角色池 5-8（轮流出场）
   - 地点：常驻基地 1-2 + 游历地点 6-10（按等级段分配，前期/中期/后期）
   - 社会群体：4-6 个（各有立场，制造冲突素材）
   - 环境威胁：3-5 个（辐射风暴/沙暴/传染病等）
   - 物件：核心道具 2-3（有来历有去向）+ 环境物件池
2. **结局规划表**：每个分支 = 1 个无条件主结局 + 2-4 个条件结局（flag 组合）
3. **伏笔规划表**：每 100 级 1 个长伏笔（跨段回收）+ 3 个短伏笔（段内回收）
4. **choice 规划表**：按三层设计列出（等级 / 类型 / 影响）

**硬规则：**
- 伏笔 flag 命名 `foreshadow_*`（validate_quality.cjs 据此查回收率）
- **伏笔必须同路径可回收**（回收事件在玩家必然能触发的路径上；跨分支伏笔要么不做要么明示"可选回收"）
- 每个分支最后一条 Lv500 事件 **FlagRequire 必须留空**（无条件兜底），且放在该分支**最后一行**（引擎取分支内最后满足事件）

### Stage 1.7：状态文件初始化

按 `references/state-file-spec.md` 在 `scenarios_wip/{id}/` 初始化：
- `meta.md`：frontmatter（独立文件，不含任何 ## 节——merge.cjs 要求）
- `content.md`：## Titles + ## Achievements + ## HolidayEvents 三段（一次性写好）
- `state.md`：进行中状态（含全部规划表）
- `log.md` + `batches/`

> 注意：副本 id 不得与 `scenarios/` 或 `scenarios_user/` 下已有副本重复，否则 merge 会覆盖正式文件。

## 三稿制生成流程

> 原则：**一小段一小段来**。每批 20-50 条（一个完整剧情小节），生成完**全量展示**给你确认。宁可批多次、时间长，不要一次生成一大堆（会产生"卡住"错觉，且错漏难查）。

**批次切分方式（重要）：** 参考废土结构——共享开头（Lv.1-5）先写，然后**分支逐一串行**（写完分支 A 全部等级，再写分支 B……），每批 = 单分支的一个等级段（20-50 条）。state.md 的进度记录必须带分支名（如"survivor 已到 Lv.x"），保证续写断点无歧义。

### 粗稿轮（保结构）

逐批循环（每批 ≈ 20-50 条事件，按剧情小节自然分片）：

```
1. 读 state.md → 确认本批范围（哪个分支的哪个等级段）与承接 → 写本批骨架，如：
   骨架（Lv.11-30，survivor）：①离开山谷 ②首次遇到商队 ③埋伏笔"铜钥匙" ④夜袭事件 ⑤小高潮：救下商人
2. 用户确认骨架 → 生成事件文本（结构优先：ID 连续、flag 正确、伏笔到位，文笔平实即可）
   写入批次文件（## Events 节 + 完整 20 列表，格式见 state-file-spec）
3. 全量展示：本批事件全文 + 本批 flag/伏笔变化 + 与上批的承接
4. 用户点头 → 更新 state.md → 下一批
   用户要改 → 当场改 → 再确认
5. 每 5-6 批（约 100 级）做一次重型验证（见下）
```

**每批 AI 自检清单（提交展示前自查）：**
- [ ] 事件 ID 按编号规则连续，无重复/倒退
- [ ] 本批 flag 设置/引用正确（对照 state.md 的 flag 清单）
- [ ] 本批开头承接上批段尾悬念
- [ ] 到期的伏笔已回收（查伏笔池）
- [ ] 角色状态与 state.md 一致（新出场/变化/死亡都要更新）

### 重型验证（每 5-6 批一次）

```
node merge.cjs scenarios/{id}.md scenarios_wip/{id}/meta.md scenarios_wip/{id}/content.md scenarios_wip/{id}/batches/{id}_b*.md
node build.js
node validate_flags.cjs {id}
node validate_quality.cjs {id}
```

**验证结果解读：**
- `[ERROR]`：必须修复（格式/ID 重复/flag 断链/choice target 悬空），修复后重跑对应命令
- `[WARN]` 分支等级缺口 / 伏笔未回收：**生成中期属正常**（还没写到的分支/伏笔），精校轮必须清零；如缺口出现在**已写到的分支**，说明漏写了某级，需补
- 报错若来自其他副本（build 解析 scenarios/ 全部文件）：先确认错误信息中的事件 ID 是否属于本副本，不是则忽略

### 细稿轮（打磨文笔）

粗稿全部完成后，逐批对照批次文件润色：
- AI 提润色方案（描写、语气、节奏），用户点头后改
- **用户也可直接改文笔**——修改写回批次文件，AI 同步更新 state.md
- 每批细稿完同样展示确认

### 精校轮（全量收尾）

- 重新 merge + 跑全量验证：`node build.js` + `node validate_flags.cjs {id}` + `node validate_quality.cjs {id}`——**要求 0 ERROR 且 0 WARN**（伏笔回收率 100%、分支等级全覆盖）
- AI 通读全副本：角色前后矛盾、跨段承接、伏笔全部兑现、结局兜底存在
- 用户终审 → 收工

## 跨会话（续写模式）

**为什么需要跨会话：** 副本内容量大（单周目三稿 ≈ 30-50 万 token）。1M 上下文下通常一个会话跑完单周目，但：
- 4 周目全量会超 1M → 按周目切会话
- 用户中途喊停 → 随时停

**会话边界仪式（每次会话结束/中断必做）：**
1. 当前批次的批次文件写完
2. state.md 更新完毕
3. log.md 追加断点摘要（3-5 行：当前轮次/进度/下一批承接）

**续写模式开场（用户说"继续"）：**
1. 列出 `scenarios_wip/` 下的状态文件，让用户确认续哪个
2. 读 state.md + log.md 最后断点
3. 展示进度摘要（轮次/等级/批数/待办）给用户确认
4. 从断点继续（不重放旧对话内容）

## 验证与收尾

| 验证 | 命令 | 时机 |
|------|------|------|
| 合并 | `node merge.cjs scenarios/{id}.md scenarios_wip/{id}/meta.md scenarios_wip/{id}/content.md scenarios_wip/{id}/batches/{id}_b*.md` | 每 ~100 级 / 粗稿轮完成 / 精校轮收尾 |
| 构建 | `node build.js` | 合并后 |
| flag 链 | `node validate_flags.cjs {id}` | 每 ~100 级 / 精校轮 |
| 质量 | `node validate_quality.cjs {id}` | 每 ~100 级 / 精校轮（精校轮要求 0 ERROR 0 WARN） |

## 注意事项（避免翻车）

- 文件第一行必须是 `---`（不能有 BOM）
- Events 表内部**不能有空行**；每行以 `|` 开头和结尾，20 列
- choice target 事件 ID 必须在表中存在
- 事件文本不少于 10 字（build 校验）
- 所有文本用第二人称"你"写
- 不同周目内容不能重复
- 不要生成 filler 事件（机制已废弃）
- 记忆靠 `scenarios_wip/` 状态文件，**不靠对话历史**（违反会导致错漏）
