# 状态文件三件套规范（ScenarioWriter 记忆系统）

本文件定义副本生成过程中的"记忆文件"格式。AI 在生成副本的每个批次前后读写这些文件，
保证跨批次、跨会话的信息一致性——**AI 的记忆靠文件，不靠对话历史**。

## 存放位置

```
scenarios_wip/                # 制作中工作区（gitignore，不随仓库发布）
  {副本id}/                    # 每个副本一个目录（如 wasteland_middle_earth）
    state.md                  # 进行中状态（权威记忆）
    log.md                    # 会话流水账（断点摘要）
    batches/                  # 批次文件（每批一个，权威记录）
      {id}_b01.md
      {id}_b02.md
      ...
```

## 一、state.md — 进行中状态（核心）

AI 每个批次**生成前必须读**、**生成后必须更新**。格式固定如下：

```markdown
# 副本状态：{name_cn} ({id})

## 基本信息
- 模式：原创 / 改编
- 副本设定：{一句话}
- 分支：{分支名列表}
- 节奏分段：{分段表：等级区间→阶段名→叙事任务}
- 风格指纹（改编模式）：{叙述温度/对白规则/节奏型/视角策略}

## 规划表（Stage 1.6 确认后写入，不再变动）
### 世界观锚点表
| 类型 | 名称 | 说明 |
|------|------|------|
| 核心角色 | ... | 弧线：出场→变化→结局 |
| 配角池 | ... | 轮流出场 |
| 地点 | ... | 分配等级段 |
| 社会群体 | ... | 立场 |
| 环境威胁 | ... | 机制 |
| 物件 | ... | 来历/去向 |

### 结局规划表
| 分支 | 主结局(无条件) | 条件结局(flag组合) |
|------|--------------|-------------------|
| ... | ... | ... |

### choice 规划表
| 等级 | 类型(态度/路径/命运) | 内容 | 影响 |
|------|-------------------|------|------|

### 伏笔规划表
| 伏笔 flag | 埋点等级 | 计划回收等级 | 类型(长/短) | 状态 |
|-----------|---------|-------------|------------|------|
| foreshadow_gift | Lv.30 | Lv.450 | 长 | 待埋 |

## 生成进度
- 当前轮次：粗稿 / 细稿 / 精校
- 批次切分方式：共享开头（Lv.1-5，含分支抉择 target）→ 分支逐一串行（每批 = 单分支的等级段）
- 批次规划表：第 n 批 = {分支} Lv.{x}-{y}（状态：未写/已粗稿/已细稿/已改）——批次总数与细稿进度以此表为准
- 已生成：{分支} Lv.{x}-{y}（第 {n}/{总} 批）
- 下一批起点：{分支} Lv.{y+1}（承接：{上一批段尾悬念}——完整承接信息在上一批批次文件的「承接」节）

## 事件编号
- 主线编号已用到（全局最大）：e{XXXX}
- 使用的编号规则：{id}_e{XXXX}（主线）/ {id}_e{XXXX}a-d（choice target）
- **编号全局单调递增，跨批次、跨分支续接**（分支 B 从 e0501 起续接，禁止回到已用编号）——validate_quality 按文件顺序检查编号倒退

## Flag 清单（全部）
| flag | 值 | 设置事件 | 用途 | 状态 |
|------|----|---------|------|------|
| fed_wangcai | true | e0057 | 命运 | 已设置 |
| foreshadow_gift | 1 | e0030 | 伏笔 | 待回收 |

## 伏笔池
| 伏笔 flag | 埋点事件 | 计划回收等级 | 状态 |
|-----------|---------|-------------|------|
| foreshadow_gift | e0030 | Lv.450 | 待回收 |

## 角色状态
| 角色 | 状态（出场/变化/受伤/死亡） | 最后出现事件 | 弧线计划 |
|------|--------------------------|-------------|---------|
| 山姆 | 活跃，忠诚 | e0120 | 结局：同归 |

## 世界观锚点使用记录
- 已登场地点：{列表}
- 已登场群体：{列表}
- 已回收物件：{列表}

## 待办/注意
- {下一批的注意点，如"上批埋的伏笔 X 到期需回收"}
```

**更新规则：** 每批完成后必须更新：进度、编号、flag 清单、伏笔池、角色状态、待办。
**读规则：** 每批开始前重读 state.md（这是唯一权威记忆，禁止凭对话历史猜）。

## 二、batches/ — 批次文件（权威记录）

每批一个文件，是**该批内容的完整记录**。**格式必须与最终 .md 的 Events 表一致**（`## Events` 节 + 完整 20 列 pipe 行），这样 `merge.cjs` 可以直接合并批次文件。用途：
1. 粗稿轮"重型验证"时 merge.cjs 直接合并（批次文件即源）
2. 细稿轮对照（逐批润色）
3. 精校轮通读
4. 续写模式恢复（避免重放旧对话）

命名：`{id}_b{三位序号}.md`（b001、b002...——三位数防止超 99 批时字典序错乱）

格式：

```markdown
# 批次 {n}：{分支} Lv.{x}-{y}（{小节名}）

## Events

| ID | Type | MinLevel | MinHours | Weight | Once | Branch | FlagSet | FlagRequire | CompletionTitle | Choice1 | Choice1Target | Choice2 | Choice2Target | Choice3 | Choice3Target | Choice4 | Choice4Target | Action | Text |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| {id}_e0001 | story | 1 | 0 | 1 | 是 | | | | | | | | | | | | | 觉醒 | 你睁开眼睛... |
| ...（本批全部事件，每行 20 列完整） |

## 承接（本批元信息，merge 会忽略此节）

- 上批结尾：{一句话悬念}
- 本批开头如何接：{一句话}
- 设置的 flag：{列表}
- 埋的伏笔：{列表}
- 回收的伏笔：{列表}
- 角色变化：{列表}
- 段尾悬念（给下批）：{一句话}
- 用户修改记录（细稿轮）：{用户改了什么}
```

> **注意**：`## Events` 必须是本批次文件**第一个 `##` 节**，**标题必须一字不差地写 `## Events`**（merge.cjs 精确匹配，写 `## Events（Lv.11-30）` 会整批静默丢失）；表内禁止插入任何 `##`/`###` 标题行（merge.cjs 遇到 `## ` 即停止 Events 提取，插入标题会导致后续事件静默丢失）；"承接"等元信息节必须放在 Events 之后，merge.cjs 不会把它们当事件行。

**多周目副本**：如需 MinRebirth 区分周目，在 Once 后插入 MinRebirth 列（共 21 列），表头与行都带上。

## 三、log.md — 会话流水账（断点摘要）

记录每个会话做了什么，用于续写模式的开场。

```markdown
# 生成流水账：{副本id}

## 会话 1（{日期}）
- 完成：规划阶段全部确认（锚点表/结局表/伏笔表/choice表/节奏表）
- 状态文件已初始化
- 断点：即将开始粗稿轮第 1 批（Lv.1-15）

## 会话 2（{日期}）
- 完成：粗稿 Lv.1-90（6 批）
- 用户修改：第 3 批"黑骑士"段落语气加强
- 断点：下一批从 Lv.91 开始，承接"你离开瑞文戴尔"
```

**断点摘要格式（每次会话结束必写）：**
```
断点：{当前轮次} / 已到 Lv.{x} / 第 {n} 批 / {一句话状态}
下一批要点：{承接 + 待办}
```

## 读写规则（AI 遵守）

1. **每批生成前**：读 state.md → 确认本批范围与承接 → 写本批骨架
2. **每批生成后**：写批次文件 → 更新 state.md → （会话结束才）追加 log.md
3. **细稿轮**：对照批次文件逐批润色，用户修改**直接写回批次文件**，同时更新 state.md
4. **会话结束（无论正常/中断）**：追加 log.md 断点摘要（3-5 行）
5. **续写模式开场**：读 state.md + log.md 最后一条断点 → **再读最后一批批次文件的「承接」节**（完整承接信息）→ 展示进度给用户 → 确认后继续
6. **禁止**：凭对话历史记忆代替 state.md；跨批次重复生成已生成内容（以批次文件为准）

## 与场景文件的关系

**meta 文件（第一批生成前就写好，merge 必需）：**
```
scenarios_wip/{id}/
  meta.md        # 仅 frontmatter（--- 包裹，不含任何 ## 节）——merge.cjs 要求 frontmatter 独立成文件
  content.md     # ## Titles + ## Achievements + ## HolidayEvents 三段（可一个文件，merge 会分别提取）
  state.md
  log.md
  batches/
```
- meta.md 与 content.md 在规划阶段（Stage 1.6 确认后）一次性写好，之后不修改（内容微调除外）
- 最终合并命令（batches 传**目录**，merge.cjs 自动按文件名排序展开；Windows/Node 不支持通配符）：
  `node merge.cjs scenarios/{id}.md scenarios_wip/{id}/meta.md scenarios_wip/{id}/content.md scenarios_wip/{id}/batches`

- 批次文件是**中间产物**，由 merge.cjs 合并为 `scenarios/{id}.md`（每 5-6 批合并验证一次，粗稿轮完成后再合并一次）
- 合并后批次文件保留（细稿轮/精校轮还要用），副本发布后才可清理
